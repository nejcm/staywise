## 1. Purpose and boundaries

Build the smallest useful guest portal for independent villa owners and small property managers (roughly 1–10 properties). A guest opens a mobile web guide from a link or printed QR code, finds property information, optionally asks a property-specific question, and can report an issue. A host edits the guide and reviews unanswered questions and reports in one inbox.

The working hypothesis is that this reduces repetitive guest-support effort. The product brief identifies issue handling as a possible wedge, but current Touch Stay materials describe guest issue reporting, chatbot-created tasks, task statuses, and a task board already. Treat issue handling as a behavior to validate with hosts, not a proven competitive gap. Touch Stay also now promotes a journey-based, mobile-first guidebook with stage-specific information and actions. [Touch Stay 2026 release](https://touchstay.com/product-updates/big-release-2026), [Task Management](https://help.touchstay.com/en/articles/15378976-task-management)

**In scope:** invite-only host sign-in, **self-serve** property setup/editing with first-party setup instrumentation, guest guide, revocable share link/QR, stored host-reviewed translations for a few enabled guest languages, direct guest questions and issue submission to one host inbox with a minimal host email alert, optional follow-up email, aggregate guest-side counters, a reservation-aware schema, a validated write path shaped as the future token ingestion API, privacy/security controls, and a five-host self-serve pilot. The first pilot has no guest-facing AI, no image uploads, and no booking-system integrations.

**Out of scope for the pilot:** PMS/reservation integrations, OTA-direct APIs, listing-URL fetching (rejected outright — OTA terms forbid automated collection), iCal feeds, email-forward reservation parsing, token-API exposure, per-stay link distribution, guest accounts, native apps, payments, upsells, review campaigns, imported guide generation, broad team/role management, AI chatbot, runtime translation, image uploads, offline caching, automated guest email/SMS, and autonomous repair or safety decisions. Add these only when pilot evidence identifies a blocker.

### Recommendations

- Build deterministic guide, translation, question/report, and host inbox flows first. AI is disabled for the first pilot; revisit only if evidence shows the saved guide plus direct host workflow does not solve recurring support work.
- Treat the validated write path as the future ingestion API: one server-side layer that validates, revises, and stores content and reservation data, whatever calls it (host editor now; scoped tokens, PMS workers, and webhook recipes later). Reservations stay empty during the pilot. See [booking_integration_research.md](../docs/booking_integration_research.md).
- Design for anonymous guests: no guest-facing feature requires identity; reservation context (name, locale, dates, party size) is a strictly optional enhancement. Reject server-side OTA fetching; treat email-forward reservation parsing as a documented, host-confirmed fallback only.
- Translate eligible guide text once per source revision for a small host-selected set of locales, store it, require review, and serve it locally. Do not make translation calls on guest page views.
- Use one app, one production Supabase project, and a separate isolated staging project with synthetic data. Keep property content in a private database schema and authorize every read/write server-side; avoid public database RPCs and broad service-role access.
- Use local Supabase CLI for development; deploy previews use only isolated staging. Frankfurt is the target region for both managed projects and production functions. Frankfurt placement is a data-location setting, not proof of GDPR compliance.
- Keep UI dependencies small. Use semantic HTML/native forms where sufficient, a runtime schema validator on server boundaries, and only accessible UI primitives that actual screens need.

## 4. Architecture and data boundaries

### Request and data flow

Guest flow: browser opens the property route with a public share ID and a secret in the URL fragment; same-origin exchange verifies the secret and sets a separate HttpOnly guest session; subsequent guest guide, question, and issue requests pass through TanStack Start server functions, which validate the session and active link, run parameterized SQL, and return only an allowlisted guest DTO. Guests are always anonymous: no feature requires identity; when a future sync supplies reservation context it is an optional enhancement, and "Guest" is the default label.

Host flow: Supabase magic-link sign-in uses PKCE; before requesting the link, the server stores the PKCE code verifier in a short-lived Secure, HttpOnly, SameSite=Lax cookie. The callback must arrive in that same browser/device, receives a one-use `?code=`, exchanges it server-side with `exchangeCodeForSession`, then redirects to the fixed `/host` path without the code; never accept a request-supplied `next` or redirect destination. If the verifier cookie is absent (for example, the link opens on another device), show a clear restart/resend path; never fall back to implicit flow. Store the resulting host session in Secure, HttpOnly, SameSite=Lax cookies scoped to `/`, with Max-Age aligned to the configured finite Supabase session lifetime. Delete the verifier cookie after callback success or failure. Use a request-scoped server auth client/custom cookie adapter; do not ship a browser Supabase Auth client or assume `@supabase/ssr` cookies are HttpOnly by default. Each server function verifies current identity and required assurance level, checks property ownership, and runs parameterized SQL through the limited runtime role.

Translation flow: host explicitly requests a draft; one server egress allowlist sends eligible guest prose to the Google EU endpoint; result is stored by locale and source revision; host reviews and publishes it.

Never return database rows wholesale. Guest responses omit host notes, account IDs, drafts/stale translations, issues, questions, and protected fields. Keep database credentials, token-HMAC key, SMTP credentials, and translation credentials server-only. Do not use a service-role key in the runtime app.

### Minimum data model

- properties: owner ID, display name, timezone, source locale, publish/disable status, timestamps.
- property_members or a single owner reference initially; no broad team role model until a pilot need appears.
- guide_sections: property, category/key, title, source text, visibility class, display order, source revision, publish state, update time. Categories: arrival/access, Wi-Fi, parking, rules, appliances, waste, checkout, emergency contacts, local tips.
- guide_translations: section, locale, translated title/body, exact source revision, provider metadata, draft/approved state, reviewer/time. A translation is current only when its source revision matches.
- share_links: public random ID, HMAC digest of the secret using an application-held key, property, enabled/rotation timestamps. Never store the raw secret or send a request-derived digest to SQL.
- guest_sessions: hash of a separate random session identifier, share-link ID, created/last-seen/expiry. Check the link remains enabled on every request; rotation invalidates its sessions.
- issues and questions: property, source text, category where relevant, optional follow-up email marked unverified, created time, new/handled state and handled metadata. No images or AI transcripts in first pilot.
- rate_limits: short-lived keyed fingerprints for link, guest session, and optional trusted IP plus atomic fixed-window counters. Do not persist raw guest IPs.
- audit_events: minimal host actions such as publish, unpublish, rotate link, delete, inbox state changes, sign-in outcomes, MFA enrollment/unenrollment, and repeated Auth callback failures. Do not store guest message bodies, raw emails, codes, tokens, or credentials here.
- reservations (empty in the pilot): property, source, external_id (unique with source), stay start/end, optional guest first name, locale, and party size; no raw payload; deleted ~90 days after stay end.
- api_tokens (created now, no routes): account, hashed token, scopes (`content:write`, `reservations:write`), optional property binding, created/rotated/last-used timestamps.
- setup_events (pilot instrumentation): host, event type, property, section/step, timestamp; host-scoped only, 90-day retention.
- guest counters: per-property daily aggregate counts (link exchanges, guide opens, submissions) with no identifiers.

Use foreign keys, valid-state constraints, indexes on property/owner and newest-first inbox time. Guests are anonymous by default: no guest-facing feature requires identity, and guest messages, counters, and rate-limit records persist no guest identifier. Reservation rows exist only to enrich context when a future sync or host-confirmed import supplies them. Request an email only when the guest explicitly asks for a reply.

### Localization: translate once and store

1. Host selects the source locale and enables at most three target locales for the pilot; choose them from recruited hosts' guest mix and reviewer availability.
2. On an explicit host action, translate only changed, eligible guide prose for enabled locales. Save output with the source revision. There are no translation calls while guests read the guide.
3. Editing source text marks its translations stale. Do not serve stale text as current. Until regenerated and reviewed, show source language and make that fallback clear, or hide the locale option for that section.
4. Host sees source and draft side by side, edits/approves the translation, and previews each locale. Qualified human review is mandatory for access, emergency, safety, and legally meaningful instructions.
5. Exclude access codes, Wi-Fi passwords, contact names, phone numbers, email addresses, third-party details, host-only notes, and all guest-submitted questions/issues from translation requests. Keep secrets in structured fields and render values without translating them. Scan free prose before egress for secret-like/high-entropy strings and contact details; block or require host correction/confirmation. This catches common mistakes but does not prove text is free of personal data.
6. Centralize provider calls behind one server egress allowlist; test exact serialized payloads for forbidden values. Do not rely on prompts or post-hoc regex scrubbing. Before the first Google request, review its current data-use/retention terms, regional endpoint behavior, and applicable DPA/transfer terms.
7. Keep small static host UI dictionaries local and test locale-key parity. The Mavi pattern is useful; no large i18n dependency is justified for the pilot.

### Security, privacy, and safety

1. Guest links are bearer credentials. Generate a 256-bit random secret; place public share ID in the route and secret in URL fragment so the secret is not sent in the HTTP request or referrer. Exchange it once with a same-origin POST. Server fetches the stored HMAC by share ID and compares in memory with a constant-time function; never put the raw secret or its digest in SQL parameters, logs, analytics, or errors. Return the same generic denial for unknown ID and bad secret. Exchange sets a separate random session cookie with Secure, HttpOnly, SameSite=Lax, narrow path, and short expiry. Recheck session plus active link on every read; disabling/rotating invalidates sessions.
2. Host accounts are invite-only; disable public signup. Use Supabase Auth magic links with PKCE, short expiry, single-use codes, exact allowlisted redirect URI, custom SMTP, and rate limits. Configure a 30-day time-boxed host session and 14-day inactivity timeout as initial values; session limits are enforced at refresh, so verify effective expiry rather than assuming immediate termination when settings change. Align the host cookie Max-Age to the 30-day time box. Exchange the callback code server-side and keep tokens in HttpOnly cookies through a server-only auth client; verify callback, cookie flags, refresh, logout, and redaction behavior. Do not log auth codes or tokens. Verify identity server-side on every request. Require TOTP MFA; allow an AAL1 session only for initial MFA enrollment, then require AAL2 for the host workspace and for access to structured access secrets or publish/unpublish/delete/rotate/security changes. Never trust client-supplied owner IDs.
3. Put application tables in a non-exposed schema. Disable the Data API because the app uses direct SQL only; keep anon/authenticated grants revoked and do not create guest SECURITY DEFINER RPCs. Connect only from server functions using a dedicated limited PostgreSQL runtime role and parameterized SQL. Enable and force RLS on every application table; runtime role must not own tables, be superuser, or have BYPASSRLS. Use validated transaction-local owner/link context. This context is trusted server input: RLS catches omitted tenant filters but is not an independent boundary against a compromised app/runtime credential. Use a separate migration/owner credential only in migration workflows. No broad Supabase service-role key at runtime.
4. Use Supavisor transaction pooler with a conservative client pool, `sslmode=verify-full`, the project's root certificate, and driver settings compatible with transaction mode. Keep state in a single transaction; do not rely on session variables, connection affinity, session-level advisory locks, temporary tables, LISTEN/NOTIFY, or unsupported prepared statements. Use atomic upserts or transaction-scoped advisory locks for limits. If selected driver has a transaction/pipelining hazard, switch drivers before feature work.
5. Make all app-data mutations in server functions POST-only; GET handlers must be read-only. The sole GET exception is the `/auth/callback` route (not a server function), which validates the PKCE verifier and one-use code, sets the host session cookie, clears the verifier cookie, and redirects to fixed `/host`. App-data mutations validate exact Origin, JSON content type, input schema, and CSRF for cookie-authenticated requests. The initial guest-link exchange happens before a session exists, so it instead requires a same-origin POST plus the valid bearer secret. Do not add a custom src/start.ts override that removes TanStack defaults. Every server function rechecks auth/authorization within the handler; route guards are not security.
6. First migration revokes default Data API grants, enables and forces RLS, then grants exact runtime operations. Set safe default privileges for future tables. pgTAP asserts allow/deny for each role/property, including tables created after initial setup. Run database tests locally, not through transaction pooler. Verify Supabase Auth still works with Data API disabled in staging.
7. One module owns external translation and any future AI calls. Only approved egress-eligible guide prose leaves the app. Do not send access/Wi-Fi secrets, contact details, third-party personal data, host notes, guest questions/reports, or images. Run structural exclusions and pre-egress secret/contact checks; test exact serialized payloads.
8. Enforce durable, atomic per-link, per-session, and property rate limits. Key session limits from an HMAC of the random guest session ID; do not persist the raw session ID in rate rows. Add an IP dimension only when the deployed TanStack/Netlify adapter exposes a trusted invocation IP; never trust client-supplied `X-Forwarded-For`. Add the "answer was in the guide?" tag to questions, and per-property daily aggregate counters for link exchanges, guide opens, and submissions (no guest identifiers, no third-party analytics).

**Acceptance:** each valid message is stored once in the correct property; invalid/oversized/cross-property/rate-limited calls are denied with usable errors; guest is not promised immediate response; optional email is stored only by explicit request and shown as unverified; host action is audited; deletion is available before retention expiry; issue intake works if translation is unavailable; alert emails carry no guest content and their delivery failure loses no inbox item; counters are aggregate-only.

### Phase 7 — Hardening and controlled pilot (3–5 days setup; 2–4 weeks use)

**Work:** Use synthetic staging content, complete restore and 90-day cleanup rehearsal, inspect deployed headers/region/runtime, run security and WCAG checks, validate log redaction. Hosts onboard themselves; verify each published field, translation, emergency contact, and link-rotation path as they finish, recording every assistance request as a support-request event rather than silent help. Observe per-step setup time from setup_events and guest use from aggregate counters only. Define the kill switch and host-alert path; test price only after actual use.

**Measures:** per-step setup time, support requests per host, time to first published guide, second-property time via copy, guide opens, question/report volume, share of questions tagged "already in the guide", host response time and effort per report, translation corrections, revocation/deletion events, and paid continuation commitment.

**Continue/stop gate:** continue only if **both** hold — at least two of five hosts make concrete paid continuation commitments after guest use, and at least three of five hosts published unassisted (zero support requests) within the 60-minute bar. If fewer than three published unassisted, host-supplied content-in (paste/upload/clone, drafting assist with AI) becomes the next build rather than feature expansion. If guides are viewed but the inbox workflow is not useful, interview hosts before adding features. If fewer than two commit, revisit buyer/problem/price before integrations or AI.

### Phase 8 — Optional AI after pilot

This phase is not required for the first pilot. Start only if hosts identify recurring questions that stored guides plus direct host follow-up do not solve.

If approved, compare provider terms, regional processing, retention, language quality, latency, and costs. Use one server-only provider path, one-turn calls, no tools/web/action execution/persistent transcript, only approved non-sensitive source sections, validated section references, abstention/escalation, per-property opt-in, and a hard app-side monthly budget. Answers come only from host-approved guide content; reservation data is optional context, never a property-fact source, and anonymous guests are served identically to identified ones. Match competitor baselines: visible re-index latency (~8 hours), usage limits per plan, and processor disclosure in the privacy notice. Preserve human fallback and direct issue form. If OpenAI is evaluated, account for default abuse-monitoring retention even with store:false; do not describe it as zero retention. [OpenAI API data controls](https://developers.openai.com/api/docs/guides/your-data?product=service)

**Release gate:** at least 30 representative answerable, missing, ambiguous, unrelated, sensitive, prompt-injection, and translated questions reviewed by hosts; zero critical inventions about access codes, emergencies, or unsafe repairs; answer quality is identical with and without reservation context. Add full-text/vector retrieval only if evaluation demonstrates that direct bounded guide context misses relevant facts.

### Post-pilot, demand-triggered (no phase commitment)

- **Content-in (first build if the setup gate fails):** host-supplied import — paste/upload an existing guide (PDF/text), clone/import from a competitor export, templates; drafting assist arrives with AI. Never server-side fetching of OTA listings.
- **First PMS sync:** selected from pilot hosts' tooling among self-serve API vendors (Beds24, Lodgify, Hosthub, Hospitable) or Smoobu via its contact gate; built as a competitor-parity key-paste sync against the canonical write layer; PMS webhooks can push into the token API earlier. Partner-gated vendors (OwnerRez multi-account, Hostaway, Guesty) only if pilot hosts use them.
- **Email-forward assist:** host forwards booking mail → pre-filled stay details await host confirmation → saved as a reservation row; reservation code as dedupe key; never automated guest-facing actions; for OTA-only hosts.
- **Token API exposure:** when a real consumer exists.
- **Access codes:** decide store-vs-pass-through at first integration (dynamic per-stay lock codes vs host-entered static); codes never stored beyond retention and never in translation or AI egress.
- **Per-stay links:** generic link remains the baseline; stay-bound links/sessions use the reservation-aware schema when context exists.
- **iCal:** only if stay-date awareness is explicitly demanded; dates only, never guest identity.

## 6. Verification plan

Run these checks as the relevant features are implemented. This document is a plan; the application does not exist yet.

- **Toolchain:** exact Bun pin and frozen install; exact TanStack patched dependency tree; advisory check; TypeScript typecheck; lint with warnings denied; format check; unused dependency check.
- **Database:** clean migrations; grants/default privileges; pgTAP allow/deny matrix for anon, authenticated, runtime, migration owner, two unrelated hosts, and a table created after initial defaults.
- **Guest access:** malformed ID, invalid secret, expired/disabled link, rotation, session replay, cookie flags, generic denial, no token in logs/referer/client errors, no secret in HTML/API output.
- **Server functions:** invoke handlers directly without loading route; missing auth, wrong owner, insufficient AAL, invalid Origin/content type, malformed/oversized body, duplicate submission, and stale session. Verify state changes reject GET and accept only intended POST requests.
- **Host Auth:** PKCE callback uses a one-use query code exchanged server-side; verifier cookie uses SameSite=Lax and works across the supported mail-client handoff; callback clears verifier state and redirects only to fixed `/host`; host session cookie uses `Secure; HttpOnly; SameSite=Lax; Path=/` with a 30-day Max-Age; configured 30-day time-box/14-day inactivity is enforced at refresh; ended sessions clear cookies and return to sign-in; no tokens in URL fragments, JavaScript-readable storage, logs, or client errors; concurrent near-expiry requests do not invalidate sessions; MFA bootstrap is AAL1-only and workspace access requires AAL2.
- **Guest exchange:** link-fragment exchange requires same-origin POST and valid bearer secret before setting the guest cookie; cookie-authenticated writes require CSRF and exact Origin; GET never changes app data.
- **Supabase exposure:** disable the Data API in staging and verify auth emails, callback/session exchange, and MFA still work; confirm REST/GraphQL data endpoints do not respond.
- **Setup instrumentation:** events recorded per funnel step, host-scoped, expiring after 90 days, containing no guest data.
- **Anonymous default:** no guest flow requires identity; absent reservation context degrades cleanly; "Guest" labeling; a future per-stay context never gates a feature.
- **Ingestion readiness:** reservation-aware tables exist from the first migration and stay empty; the canonical write layer validates exactly as the token API will; no token endpoints are routable.
- **Alerts and counters:** alert mail contains no guest content and delivery failure loses no inbox item; counters are aggregate-only with no identifiers.
- **Translation:** source revision invalidation, current-approved selection, source fallback, locale key parity, provider failure, and exact serialized payload exclusions for synthetic secret/contact markers.
- **Pooler:** `sslmode=verify-full` with the project root certificate; transaction-local RLS context; no handler relies on session affinity; atomic limits under concurrent requests; conservative per-instance pool; selected driver does not use unsupported prepared statements or unsafe pipelining.
- **Rate limits:** confirm deployed Netlify adapter exposes trusted invocation IP before using IP-based keys; spoofed client `X-Forwarded-For` never changes the trusted value. Link/session/property counters remain active if no trusted IP is exposed; verify session and aggregate caps return a clear backpressure response.
- **Retention/recovery:** idempotent cleanup for 90-day guest-message, audit, and setup-event retention; reservation deletion ~90 days after stay end; 30-day disabled-link metadata; expiry of sessions/rate windows; deletion of old link digests on disable/rotation; translation metadata cascade deletion; and restore rehearsal followed by cleanup before guest traffic reopens.

## 7. Rollout and release gates

1. **Local:** local Supabase, synthetic properties, fake credentials.
2. **Internal preview:** Netlify preview points only to staging; protected preview URL; complete Auth/RLS, link-exchange, rotation, cache/header, and no-secret checks.
3. **Host preview:** one friendly host with fake QR and fake access details; test editor comprehension, draft/publish, translation review, mobile display, and PKCE email-link handoff on the supported clients.
4. **Controlled pilot:** five hosts onboard themselves; each selects exact guest-visible fields, verifies reviewed translations and emergency contacts, understands bearer-link sharing, tests revocation, and accepts the host-alert/inbox workflow.
5. **Paid continuation:** apply the combined gate (≥2/5 paid **and** ≥3/5 published unassisted within 60 minutes) against the $5–9/property/month test; do not add features before the continue/stop decision.
6. **Public launch later:** clear name/domain, review privacy and processor agreements/transfers, publish retention/deletion terms, test backups/restore and incident response, finish accessibility review, confirm real provider prices/regions, and establish host notification/support ownership.

**Phase 5 upgrade recovery (legacy locale tags).** Migration `20261019130000_phase5_translations.sql` stops, naming every offending row, while the database still holds locale tags outside the approved `en`/`de`/`sl` vocabulary or when normalization would collapse two stored translations onto one locale. A failed run commits nothing; the migration itself never rewrites prose, deletes rows, or guesses a language.

- Supported regional tags (`en-US`, `de-AT`, `sl-SI`) normalize automatically to their base language; no action is needed.
- A tag that was already wrong metadata for approved-language prose can be corrected directly: `update app.properties set source_locale = '<en|de|sl>' where id = '<property id>';`
- Genuine unsupported-language prose is never relabelled into `en`/`de`/`sl` by a tag change. The owner either keeps the upgrade blocked and exports the property, or translates/reviews the actual source content, invalidates the translations produced from the old source (a source edit through the editor bumps `guide_sections.source_revision`; otherwise delete or redraft those rows), and only then corrects the tag.
- An unsupported stored translation locale cannot be served under the vocabulary: delete or retranslate those rows.
- When normalization would collapse rows (for example both `sl` and `sl-SI` on one section), keep one row per locale.

Re-run the migration after the corrections; it remains all-or-nothing until they succeed.

## 8. Main risks and mitigations

| Risk | Mitigation / trigger to revisit |
|---|---|
| Issue handling duplicates a feature competitors sell | Do not claim novelty. Validate setup time and host time saved for small operators; Touch Stay already documents issue reporting and task management. |
| Bearer link is forwarded or indexed | Fragment-held random secret, HMAC storage, no token logging, noindex, no-referrer, revocation, and clear disclosure. Add per-stay access only if a specific host use case justifies identity/reservation data. |
| TanStack server-function vulnerability or supply-chain issue | Exact patched compatible releases, full lockfile/advisory check, and deploy gate. Do not rely on a header/WAF workaround instead of patched versions. |
| Cross-property leak | Authorization in every handler, private schema, limited DB runtime role, forced RLS, explicit guest DTOs, direct-handler and pgTAP negative tests. |
| Function/database regions mistaken for GDPR compliance | Frankfurt is a location setting only. Review provider DPAs, logs, backups, control plane, subprocessors, support access, and transfers before real data. |
| Translation changes meaning or becomes stale | Store by source revision; stale fallback to source; host approval; qualified review for access/emergency instructions. |
| Provider receives sensitive data | One egress allowlist; no secrets/contact details/third-party data/guest messages; exact payload tests. |
| Inbox response is too slow | Host email alert ships in the pilot; name an owner and publish truthful check cadence. |
| Photo upload increases privacy and abuse scope | Keep text-only pilot; add storage only after demonstrated need, strict validation, private access, deletion, and retention are ready. |
| Vendor cost/terms change | Dated price review, monthly budget, disabled auto-recharge, and procurement recheck for translation/SMTP. |
| Product name collision | Keep Staywise provisional; clear domain/legal before external launch. |
| Setup friction stalls the pilot | Self-serve by design; per-step setup events; on-request support logged as stall data; combined gate forces content-in next if fewer than three of five publish unassisted. |
| Booking-data access closed at this scale | OTA-direct APIs not pursued; PMS/webhook/ingestion-API paths documented; anonymous-first design keeps guest identity optional. [Research](../docs/booking_integration_research.md) |
| Listing-import temptation | Server-side OTA fetching rejected in writing; content-in is host-supplied only. |
| Email-forward parsing fragility | Fallback only, host-confirmed, reservation-code dedupe, no automated guest-facing actions. |
| Access codes via future sync | Open decision at first integration: dynamic pass-through vs host-entered static; never stored past retention, never in translation/AI egress. |
